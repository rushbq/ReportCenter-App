### S1 🟠 首頁戰情 SP 以欄位位置綁定底層 SP

`usp_Rpt_Home_YtdTarget` 用 `INSERT INTO #SalesRaw EXEC usp_Rpt_Sales_YtdTargetByGroup`（接單同理）取得資料。`INSERT … EXEC` 是**依欄位位置**對應，不看欄名：

- 底層 SP 新增一個欄位 → 首頁直接報錯（欄位數不符），**首頁整個打不開**。
- 底層 SP 調換兩個同型別欄位順序 → 不會報錯，但**數字會悄悄算錯**（最危險）。

兩支底層 SP 目前不在 repo，修改它們的人不一定知道首頁依賴它。

**建議**

1. 把 `usp_Rpt_Sales_YtdTargetByGroup`、`usp_Rpt_Order_YtdTargetByGroup` 也放進 `ReportCenter.Web/docs/開發/`，並在兩支 SP 的檔頭註明「被 `usp_Rpt_Home_YtdTarget` 以 INSERT…EXEC 依位置擷取，欄位異動須同步修改」。
2. 長期：把底層計算抽成共用的資料來源（例如一張每日 / 每月由排程寫入的彙總表），首頁與既有報表都讀同一張表，消除 `INSERT … EXEC` 位置耦合。

### S3 🟢 傳入非當年度時截止月不正確

SP 的截止月永遠由「系統當月」推算，不看 `@ReportYear`。若日後有頁面傳入去年（例如查 2025 年），截止月仍是今年的月份（例如 9 月），而不是 12 月，結果會少算。首頁固定傳 NULL（當年度），**目前不會觸發**。

**建議**：若要開放查歷史年度，改為 `@ReportYear < YEAR(GETDATE())` 時 `@EndMonth = 12`。

### S4 🟢 1 月選「月結累計」時首頁全為 0

截止月 = 當月 − 1 = 0，SP 設計上回傳 0 代表「上月尚未結算」。但在 1 月整個月，首頁預設以外的「月結累計」都是空的。

**可評估的替代方案**：1 月月結時改顯示「去年全年（12 月）」的結果，並在畫面標示年度。屬於業務決策，需與需求方確認。

### S5 🟢 RuleCode 是否可能跨群組重複加總

銷售底層 SP 輸出含 `GroupCode` 欄位，首頁彙總時只依 `RuleCode` 對應區塊、不看 `GroupCode`。若同一個 RuleCode 在底層輸出中出現在多個群組（例如同時出現在明細群組與小計群組），首頁會**重複加總**。從 SP 本身無法判斷，需與底層 SP 負責人確認輸出是否保證 `(RuleCode, ReportMonth)` 唯一。

### P3 分類（ReportCategory）是否需要管理 UI

**分類被哪些地方使用**

| 位置 | 用途 |
|------|------|
| 部門報表頁 | 分類 Tab（全部 / 各分類）與卡片上的分類徽章 |
| 目錄管理 — 編輯報表 | 「分類」下拉選單 |
| 權限管理 | 報表樹以分類分組 |
| 首頁「管理釘選」、全站搜尋 | 可依分類篩選 / 搜尋 |
| 使用分析 | 熱門 / 冷門清單顯示分類名稱 |

**目前資料**（開發 DB）：只有 3 個分類——目標達成（14 張）、產品銷售（19 張）、客戶銷售（15 張），另有 3 張未分類。

**評估：目前不需要開發 UI。** 理由：

- 分類只有 3 個，且是報表的大分類，變動頻率極低（一年可能不到一次）。
- 改名或新增只需一行 SQL，由維護本系統的 IT 人員執行即可：

  ```sql
  -- 新增
  INSERT INTO ReportCategory (CategoryName, SortOrder, IsActive) VALUES (N'新分類', 4, 1);
  -- 改名
  UPDATE ReportCategory SET CategoryName = N'新名稱' WHERE CategoryID = 2;
  -- 停用（不刪除；停用後報表在權限樹會歸入「未分類」）
  UPDATE ReportCategory SET IsActive = 0 WHERE CategoryID = 3;
  ```

- 刪除分類會讓報表變成未分類，用 UI 開放反而容易誤操作。

**何時值得做 UI**：分類超過約 10 個、需要頻繁調整，或要交給非 IT 人員維護時。屆時可在 `/Admin/Catalog` 加一個「分類管理」對話框（Service / Repository 的 CRUD 已存在，只缺畫面與 POST handler）。

### P4 權限頁人員樹 N+1、批次授權逐筆寫入

**問題 1：人員樹 N+1 查詢**（`PermissionService.GetDeptUserTree`）

```
GetCatalogDepartments()          → 1 次查詢（取 22 個部門）
foreach 部門: GetUsersByDepartment → 22 次查詢（每部門一次）
                                    ───────────
                                    共 23 次 PKSYS 往返
```

「N+1」指先查 1 次清單、再對清單中每一筆各查 1 次。往返次數隨部門數線性成長，每次往返都有網路延遲與連線成本。

- 目前規模：PKSYS 顯示中部門 22 個、在職 126 人；實測 `/Admin/Permission` 約 0.09 秒，**不影響使用**。
- 優化方式：改成 **2 次查詢**——部門清單 1 次 + `SearchUsers()` 一次取回全部在職人員，在記憶體中依 `DeptID` 分組（`users.GroupBy(u => u.DeptID)`）。126 人一次取回的資料量很小，改動約 10 行，查詢數從 N+1 降為固定 2。

**問題 2：批次授權逐筆寫入**（`SqlPermissionRepository.GrantPermissions`）

對「每個人 × 每張報表」各送一次 `IF NOT EXISTS … INSERT`：

| 情境 | 往返次數 |
|------|---------|
| 5 人 × 3 張（日常） | 15 |
| 30 人 × 20 張（整個部門開權限） | 600 |
| 126 人 × 51 張（極端：全員全報表） | 6,426 |

全部在同一個交易內，次數越多，交易持有 `UserReportPermission` 鎖的時間越長，期間其他人讀權限（每個頁面都會讀）會被擋住等待。

優化方式（擇一，皆相容 SQL Server 2008 R2）：

1. **集合式單一 SQL（建議）**：用 Dapper 把員編、報表編號各傳成清單，一次完成：

   ```sql
   INSERT INTO UserReportPermission (EmployeeId, ReportID, GrantedBy)
   SELECT e.EmployeeId, r.ReportID, @GrantedBy
   FROM (SELECT EmployeeId FROM ...員編清單...) e
   CROSS JOIN (SELECT ReportID FROM ReportCatalog WHERE ReportID IN @ReportIds) r
   WHERE NOT EXISTS (SELECT 1 FROM UserReportPermission p
                     WHERE p.EmployeeId = e.EmployeeId AND p.ReportID = r.ReportID);
   ```

   員編清單可用 Table-Valued Parameter（2008 已支援），或用 `UNION ALL SELECT @e0 UNION ALL SELECT @e1 …` 組成。回傳 `@@ROWCOUNT` 即為新增筆數，畫面「新增 / 略過」統計不變。
2. **Table-Valued Parameter + MERGE**：建立 TVP 型別，`MERGE … WHEN NOT MATCHED THEN INSERT`。需要在 DB 建立型別物件，部署多一步。

無論哪種，往返都從「人數 × 報表數」降為 1 次。

**建議時機**：目前日常操作量小，可在下次修改權限功能時一併處理。

## 2. 已修正（2026-10-19）

### 🔴 2.1 未通過驗證時會變成固定使用者 10308（管理員）

- **問題**：`GetCurrentUser()` 在未驗證時回傳 Mock 使用者 `10308`，該員編在管理員名單中；應用程式又沒有全域驗證要求，正式環境完全依賴 IIS 關閉匿名驗證。IIS 一旦設錯，匿名請求就能以管理員身分修改目錄與權限。
- **修正**：
  - `Program.cs`：非開發環境設定 `FallbackPolicy = 需通過驗證`，所有頁面 / API 未驗證一律 401 + Negotiate 挑戰。
  - `SqlReportService.GetCurrentUser()`：未驗證時回傳空使用者（Id 空白：非管理員、無任何權限），不再退回 Mock 使用者。

### 🟠 2.2 `dbs` 公司別參數只有部分入口會加，且可能是空值

- **問題**：部門頁、側欄收藏會加 `dbs`，首頁釘選與全站搜尋不會；且前端直接讀 cookie，沒切換過公司的人會送出 `dbs=`。
- **修正**：新增 `IReportService.GetCurrentCompanyId()`（唯一的公司別判定）與 `BuildReportUrl()`（唯一的連結組法），四個入口都改由後端組好連結，刪除前端各自拼接的程式。頂欄、側欄、部門清單、使用記錄也改用同一個公司別判定。

### 🟠 2.3 使用者預設公司固定為 `tw`

- **修正**：`UserInfo.CompanyId` 改依 PKSYS 所屬部門的 `User_Dept.Area`（TW→`tw`、SH→`sh`，查無→`tw`）。上海同仁第一次進站即看到上海部門。診斷頁也會顯示此欄位的來源。

### 🟠 2.4 收藏 / 釘選 API 不檢查權限，不存在的報表會 500

- **修正**：新增收藏 / 釘選前檢查「報表存在且啟用、使用者有權限（管理員免授權）」，不符合回 403 JSON；取消一律允許。

### 🟢 2.10 部門代碼數字防護（第二批）

`ReportDepartment.DeptID` 為 INT，PKSYS 部門代碼為字串（目前 22 個顯示中部門全為數字）。加上三道防線：

1. **啟動驗證**：`DepartmentDisplay` 任一 DeptID 非數字 → 啟動即失敗，Fatal log 寫明原因（`ValidateOnStart`）。
2. **執行期防護**：`SqlReportService.GetReports` 遇到非數字代碼記 Warning 並回傳空清單，不再當成部門 0 去查詢。
3. **資料庫型別**：`ReportDepartment.DeptID` 本身是 INT，非數字值無法寫入。

### 🟢 2.11 權限樹遺漏「分類已停用」的報表（第二批）

`GetReportTree` 只列啟用中分類，而「未分類」只收 `CategoryID` 為空的報表；分類一旦停用，底下的啟用中報表就不會出現在任何節點，管理員無法對它們批次授權。已改為：沒有分類、或分類已停用 / 不存在的報表都歸入「未分類」。（目前 3 個分類皆啟用，尚未實際發生。）

### 🟢 2.12 首頁戰情快取（原提案 S2，第三批）

- **問題**：每次開首頁、每次切換銷售 / 接單或月結 / 即時，都執行一次全年度、兩家公司的 YTD SP；首頁是全員入口，`OnGet` 同步等待 SP 完成。
- **修正**：`HomeDashboardService` 以 `IMemoryCache` 快取，key = `(Mode, CumulativeType, 日期)`；月結累計快取到當天結束、即時累計快取 5 分鐘。快取未命中時寫 Information log（含 SP 耗時）。
- **取捨**：即時累計最多落後 5 分鐘；需要立即更新時回收 App Pool。快取只在單台伺服器記憶體內。

### 🟢 2.13 部門名稱以 PKSYS 為準（原提案 P5 方案 A，第三批）

- **問題**：`ReportDepartment.DeptName` 是儲存當下的快照，PKSYS 部門改名後，管理總覽矩陣與目錄管理清單仍顯示舊名，而編輯時的勾選清單是新名，前後不一致。
- **修正**：`CatalogService.GetCatalogItems` / `GetAdminStats` 讀取後，以一次 PKSYS 部門查詢建立 `DeptID → 目前名稱` 對照覆寫顯示名稱；PKSYS 查無此部門時保留快照，已裁撤部門的歷史指派仍可辨識。DB 結構不變，下次儲存報表時快照也會更新為新名稱。

### 不處理：web.config 加入 Windows 驗證設定

評估後**不加入**。`windowsAuthentication`、`anonymousAuthentication` 屬於 IIS 預設鎖定（`overrideModeDefault="Deny"`）的設定區段，寫進站台 `web.config` 會讓站台直接回 **HTTP 500.19**，除非伺服器管理員先在 `applicationHost.config` 解除鎖定。既然 IIS 已手動設定、且應用程式有 FallbackPolicy 兜底（未驗證一律 401），加入 `web.config` 只增加部署風險、沒有額外安全效益。
